# Draft remediation plan

Prepared on 5 October 2026 from [the repository review](/home/enzo/Epita/labo/web-scraper/docs/review/2026-10-05-review.md). This records the original proposed plan. Implementation on `codex/security-remediation` is tracked in [the remediation status](/home/enzo/Epita/labo/web-scraper/docs/review/2026-10-05-remediation.md). Finding IDs refer to that report.

The first target is a safe, testable release of the existing scraper. Restore the wider advertised feature set only after the shared fetch/browser boundaries are sound. Effort estimates are rough engineering days for one maintainer and include meaningful tests; deployment constraints and feature restoration can change them.

## 1. Establish a reliable baseline and contain exposure

**Priority: immediate. Effort: 1–2 days. Findings: F05, F07, F17.**

1. Make HTTP startup reject missing/empty auth tokens. Preserve token-free stdio. Restrict any explicit unauthenticated-HTTP opt-in to loopback and document remote TLS termination.
2. Restore all ten advertised tools on the hardened shared fetch/browser layer. **Updated 6 October: the user requested preservation of all features.** Crawl, map, and persistent interaction now have bounded jobs/sessions, lifecycle cleanup, and integration coverage; see the remediation evidence for completed acceptance checks.
3. Add an integration test comparing registered MCP tools with the supported contract. Run the full suite on a clean checkout.
4. Stop tracking runtime logs and add ignore/rotation/redaction rules. Keep untracked experiments intact; decide separately whether to convert them to explicit opt-in integration scripts with `__main__` guards.

**Acceptance:** no-token and empty-token HTTP launch fail; stdio starts; wrong/missing bearer credentials are rejected under configured HTTP auth; clean-checkout pytest collects and passes; documented tool names match runtime registration.

## 2. Close the SSRF boundary at connection time

**Priority: before network-facing release. Effort: 3–5 days. Findings: F01, F02, F03, F10. Depends on stage 1 for test infrastructure.**

1. Centralize URL parsing and destination policy. Require globally routable addresses by default; reject malformed authority/ports, unsupported schemes, and userinfo unless explicitly supported. Use administrator-controlled exceptions only for intentional service integrations.
2. Implement connection-time DNS enforcement. Static HTTP connections must use an address from the approved resolution while preserving original Host/SNI/certificate verification. Re-resolve/revalidate on redirects and retries, with bounded async resolution. Explicitly handle mixed IPv4/IPv6 answers and proxy environment configuration.
3. Route Chromium through the same guarded egress policy, with no direct-network bypass. A dedicated forward proxy plus network isolation is the recommended boundary. Validate destinations at actual socket establishment, including redirected and subresource traffic. Merely validating `page.url` afterward is insufficient.
4. Disable WebSockets and service workers until they are covered by that boundary. If needed later, explicitly support ws/wss at the proxy and verify connection policy. Account for browser background traffic and other unsupported protocols.
5. Enable Chromium sandbox deliberately and verify supported host/container execution. If the environment cannot support it, move rendering to a restricted worker with an explicit minimal filesystem/network policy. Keep LLM/search integration endpoints outside caller-controlled scrape destination exceptions.

**Acceptance:** local fixture logs show zero requests to denied destinations for public-to-loopback redirects, mixed DNS, rebinding, private subresources, WebSockets and service-worker cases. Tests cover `100.64.0.0/10`, IPv6/mapped addresses, localhost aliases, public HTTPS/SNI, permitted redirects and configured proxies. Run tests with the exact Playwright/browser pair shipped in the image. A slow DNS fixture must not block unrelated requests.

## 3. Enforce memory, time and workload budgets

**Priority: before network-facing release. Effort: 2–4 days. Findings: F04, F09, F10, F16. Depends on stage 2's fetch architecture.**

1. Stream static and robots responses; enforce wire/decompressed/output byte budgets before full accumulation. Reject oversized content explicitly and handle compression with bounded allocation.
2. Add an end-to-end deadline around DNS, queue/rate waits, redirects, download, render and parse. Keep per-I/O timeouts as additional limits.
3. Bound browser work through the rendering worker: resource count/size, DOM serialization, context lifetime, memory/CPU, downloads and process termination on exceeded budgets.
4. Add global and per-client admission limits for tool calls, static fetches, parsing and LLM work; reject or queue with a bounded capacity. Set provider output budgets and model-token budgets including prompts/schemas/source text. Validate query/schema/prompt and transport-body sizes.
5. Validate all numeric settings with appropriate ranges. Add TTL/size bounds to domain and robots caches. If job/session features are retained, reserve capacity and clean up expired/cancelled work.
6. Wrap browser setup in exception-safe cleanup and recover disconnected browser state. Use context-managed LLM clients or controlled client lifetimes.

**Acceptance:** oversized chunked/compressed/multibyte and robots responses abort within configured memory bounds; slow streams stop at a total deadline; concurrent calls cannot exceed configured active/queued budgets; zero/negative configuration is rejected; setup failures/cancellation leave no contexts or workers behind. Measure responsiveness and peak memory on bounded adversarial fixtures.

## 4. Refresh dependencies and make releases verifiable

**Priority: start immediately; complete before release. Effort: 1–3 days. Findings: F06, F08, F15. Can begin before stages 2–3; final release waits for them.**

1. Refresh affected transitive versions and regenerate the frozen lockfile: AnyIO at least 4.14.2, h2 at least 4.4.1, urllib3 at least 2.8.0, PyJWT at least 2.15.0, and development virtualenv at least 21.7.13. Treat these as advisory-based starting targets, not an automatic compatibility or clean-audit guarantee.
2. Re-audit all locked packages and distinguish runtime/build/dev usage. Recheck the PyJWT record without a declared fixed release. Document any accepted unresolved finding with applicability, owner and expiry.
3. Make GitHub/GitLab publication depend on clean-checkout lint, formatting, mypy, full tests, secret scanning, dependency scanning and a fresh scan of the exact built image. Set nonzero vulnerability exit codes, and use narrow reviewed exceptions instead of blanket nonblocking settings.
4. Publish `latest` only from a protected default branch. Use immutable commit/version tags elsewhere and ensure every enabled trigger produces a valid tag set.
5. Pin third-party actions and base/build images to reviewed immutable references. Include the shipped browser and OS packages in the image inventory.
6. Generate an SPDX SBOM, sign and attest the image by digest, verify those artifacts in CI, and update README verification for the actual registry/OIDC issuer/release identity.

**Acceptance:** OSV audit and fresh image scan produce no unreviewed applicable high/critical findings; a deliberately failing test/scan prevents push; a feature-branch build cannot replace `latest`; signature and SBOM verification succeed for the same digest users pull.

## 5. Make returned data trustworthy and behavior predictable

**Priority: following the safety baseline. Effort: 2–4 days. Findings: F12, F13, F14 and additional LLM concerns.**

1. Accept only configured HTTP statuses/content types for extraction/research and return structured errors for blocked/challenge/unreadable pages. Preserve source-level failure reasons. Avoid automatic browser fallback for ordinary error responses.
2. Define a bounded content-readiness strategy for JavaScript pages and add delayed-DOM fixtures.
3. Align robots defaults with documentation; apply robots/rate policy to redirect destination origins; define robot HTTP/error semantics and expire cached rules.
4. Validate input JSON schemas and every returned structured result. Check tool names/argument shapes and provider stop reasons. Cap any repair attempt and make failures explicit.
5. Separate source text from model instructions, state that embedded source commands are untrusted, and add adversarial content fixtures. Validate report citation indices against the returned source list. Do not treat model prompting as isolation.
6. Replace provider inference and fixed context assumptions with explicit validated configuration and token budgets. Normalize Ollama URL components, including IPv6 and path handling. Correct the Anthropic/Ollama and search-precedence documentation.

**Acceptance:** numeric/required-field schema violations never return success; wrong tool calls and truncated outputs fail predictably; 404/challenge pages are not cited as factual sources; delayed JS content is extracted under a fixed deadline; robots behavior matches the configured contract; citation identifiers correspond to sources.

## 6. Restore features and maintain honest evidence

**Priority: after shared safety work. Effort: 1–2 days for documentation/benchmark cleanup; feature implementation separately estimated. Findings: F07, F17, F18.**

1. Restore crawl/map/browser interaction on the hardened fetch/browser layer. Include bounded crawl frontier/results, cancellation, expiry, session isolation, reserved browser capacity and same-origin policy. Add end-to-end tool inventory, dedup/depth/page caps and lifecycle tests.
2. Replace the background launcher with a supervised foreground process or implement configured-port/readiness/PID handling. Keep operational logs out of the repository.
3. Regenerate the four-fixture scorecard with commit/dependency/browser metadata and label its actual scope. Add representative article/product/listing/forum and malformed/error/JS fixtures; benchmark fetch/render and structured extraction separately from parser token F1.
4. Add Python compatibility coverage for supported 3.11–3.13 versions, including Docker's 3.12 and the exact shipped browser. Schedule a maintained dependency refresh process through normal project tooling.

**Acceptance:** supported features are callable and tested, results/caps remain bounded under concurrency and cancellation, benchmark output reproduces the committed evidence, and documentation describes deployed behavior.
